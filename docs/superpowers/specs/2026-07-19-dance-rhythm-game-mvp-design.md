# FullyDancy MVP 主产品蓝图

**状态：** 当前主产品蓝图，覆盖已实现原型与后续 MVP 技术路径  
**最近更新：** 2026-08-17  
**适用范围：** FullyDancy Web MVP、作品集展示、后续上线准备

## 1. 一句话产品定义

FullyDancy 是一个面向有初步练舞能力用户的 AI 舞蹈节奏练习 Web 产品，通过内置示范视频、浏览器端卡点分析、人体骨架识别和挑战前身体校准，帮助用户在居家练舞时练习“卡准节奏”和“把肢体动作做舒展”。

## 2. 产品本质与边界

FullyDancy 的本质是轻量 AI 反馈型练习工具，而不是舞蹈教学平台、专业动作纠错系统或原舞还原评分器。

产品假设用户已经能通过视频学会一段舞，真正缺的是练习反馈：动作是否卡在音乐点上、手臂有没有伸直、下蹲是否到位、动作有没有明显缩水。因此，FullyDancy 不尝试判断“跳得像不像原视频”，而是把练舞中的关键动作意图拆成可解释、可反馈、可重复练习的目标。

当前 MVP 优先验证三件事：

1. 用户是否能用一个内置舞蹈关卡完成从卡点确认到身体校准的完整流程。
2. 系统是否能用浏览器本地能力完成音频卡点、示范骨架、用户骨架和身体尺度采集。
3. 产品是否能以足够轻量的方式传达“节奏 + 肢体舒展”的核心价值。

## 3. 目标用户

首版用户是有少量翻跳经验、能自行学会一段舞的舞蹈爱好者。

他们的典型状态：

- 在家对着视频练习，通常使用电脑或大屏设备播放示范。
- 已经知道动作顺序，但动作完成度不稳定。
- 常见问题是手臂没有完全伸直、下蹲不够、动作落点不利落、卡点慢半拍。
- 希望获得接近音游或舞蹈机的即时反馈，但不希望被专业术语和长篇纠错打断。

## 4. 核心产品原则

- 节奏是玩法主干，动作状态只作为少量卡点上的附加目标。
- 产品奖励用户做对的瞬间，弱化训话式负反馈。
- 系统只判断能被稳定解释的内容，不做专业舞蹈审美评分。
- 摄像头看不清、关键点缺失或置信度不足时，不把技术失败算作用户错误。
- 挑战前自动采集身体比例和机位尺度，不要求用户手动填写身高、臂长或角度。
- 判定使用相对身体比例和关节角度，不使用屏幕绝对坐标。
- 所有视频、音频、摄像头画面、姿态点和校准数据默认只在浏览器本地处理。
- 当前 MVP 保持无账号、无后端、无数据库、无上传，优先低成本上线和作品集展示。

## 5. 当前 MVP 范围

### 5.1 当前已包含

- 唯一内置舞蹈关卡：`8月3日舞蹈挑战`。
- 首页 Canvas 荧光粒子舞者动效。
- 关卡选择页：内置关卡可选，上传入口禁用。
- 内置视频音轨分析，生成少量候选卡点。
- 卡点分析页单时间轴：荧光卡点 + 白色视频进度点。
- 卡点操作：卡节奏、手臂打开、下蹲、删除。
- 卡点与视频联动：点击时间轴、卡点或卡点操作均跳转视频时刻。
- 示范视频全程骨架缓存，并在卡点附近显示骨架叠加。
- 手臂打开 / 下蹲卡点的示范骨架关键部位高亮。
- 身体校准页：摄像头、实时骨架、三步轻量采样。
- 最小校准档案：肩宽、髋宽、身体高度、臂展、镜头尺度、采集时间。
- 极简挑战页壳子：示范视频、摄像头舞台占位、已载入卡点数。
- React 会话内流程闭环：`首页 → 关卡选择 → 卡点分析 → 身体校准 → 舞蹈挑战`。

### 5.2 当前明确不包含

- 真正的用户视频上传。
- 多关卡管理和关卡后台。
- 账号、云同步、排行榜、社区分享。
- 正式节奏评分、Combo、能量、战绩卡。
- 再来一局 2 秒机位复核。
- 专业逐帧姿势相似度评分。
- 自动识别舞种、动作语义或原视频编舞结构。
- 录屏、视频导出、手势控制播放。

## 6. 信息架构与页面设计

### 6.1 首页 `HomeScreen`

目标：用最短路径建立产品气质，并把用户引导到正式流程。

内容：

- 品牌：`FullyDancy`。
- 状态文案：`Dance practice`。
- 首页主标题：`把动作跳开`。
- 说明文案：`跟着音乐，把每一个动作做到更舒展。`
- 隐私提示：`视频和摄像头数据仅在本地处理`。
- 主操作：`开始游戏`。
- 背景：`ParticleDancerHero` Canvas 粒子舞者动效。

交互：

- 点击 `开始游戏` 后进入关卡选择页。
- 首页不申请摄像头权限。
- 首页不暴露调试入口、模型档位或性能数据。

动效：

- 粒子在黑色舞台背景上自由漂浮。
- 粒子周期性凝聚为抽象舞者轮廓。
- 动效用于表达“意识流、节奏、身体舒展”，不能遮挡主标题和按钮。
- 支持 `prefers-reduced-motion`，减少动态用户进入低动效状态。

### 6.2 关卡选择页 `LevelSelectScreen`

目标：保持 MVP 极简，同时让用户知道未来可能支持自定义上传。

内容：

- 页面标题：`选择你的挑战`。
- 可用关卡：`8月3日舞蹈挑战`。
- 内置关卡说明：`内置练习 · 45 秒`。
- 禁用入口：`上传自己的舞蹈（即将开放）`。

交互：

- 点击内置关卡进入卡点分析页。
- 点击返回回到首页。
- 上传入口必须是禁用按钮，不打开文件选择器，不接受拖放，不调用上传逻辑。

### 6.3 卡点分析页 `AnalysisScreen`

目标：让用户用最少操作确认“这段舞要在哪些音乐点练什么动作”。

页面结构：

- 顶部：返回、品牌、步骤 `02 / 04`。
- 主体：大尺寸示范视频。
- 视频叠加层：示范骨架。
- 底部：单一时间轴、选中卡点操作、确认按钮和示范骨架提取状态。

时间轴规则：

- 页面只保留一条产品时间轴，不显示第二套视频进度条。
- 荧光大点代表候选卡点。
- 白色小点代表当前视频播放进度。
- 时间轴点击任意位置，视频跳到对应时刻。
- 点击卡点，视频跳到该卡点时刻，并选中该卡点。
- 点击卡点下方操作，也跳到该卡点时刻。

卡点操作：

- 只显示当前选中卡点的操作项，避免大量操作占据视频区域。
- 操作项包括：
  - `卡节奏`
  - `手臂打开`
  - `下蹲`
  - `删除`
- 同一卡点同一时间只允许一个动作状态。
- 删除后该卡点变为 disabled，不参与后续挑战。

音频分析：

- 用户点击 `分析卡点` 后，系统读取内置视频音轨。
- 使用轻量能量峰值算法生成候选卡点。
- 不预设谱面，不自动标注原视频动作语义。

示范骨架：

- 分析后启动示范视频全程骨架缓存。
- 根据当前视频时间寻找最近姿态帧。
- 如果当前卡点是 `手臂打开`，高亮示范骨架手臂。
- 如果当前卡点是 `下蹲`，高亮示范骨架下肢。

错误状态：

- 音轨或关卡加载失败时显示 `关卡加载失败，请重试`。
- 保留重试入口，不清空已选择关卡。

### 6.4 身体校准页 `CalibrationScreen`

目标：在挑战前自动记录用户身体尺度，降低镜头距离、身高和体型差异带来的误差。

页面结构：

- 顶部：品牌、步骤 `03 / 04`。
- 左侧：校准说明和三步列表。
- 右侧：摄像头画面和实时骨架叠加。
- 底部：状态提示和 `开始校准` 按钮。

校准步骤：

1. **全身入镜**：引导用户后退或调整机位，让手脚尽量完整入镜。
2. **站直记录**：记录肩宽、髋宽、身体高度和站立尺度。
3. **四肢展开**：记录手臂自然打开时的最大臂展。

交互：

- 进入该页时页面尚不自动申请摄像头。
- 用户点击 `开始校准` 后申请摄像头权限。
- 运行期间按钮显示 `校准中…`。
- 系统通过 `hasFullBodyInFrame` 判断关键点是否可见。
- 每步按短采样窗口推进，生成 `CalibrationProfile`。
- 校准完成后触发 `onComplete(profile)`，进入挑战页。

当前校准档案：

```ts
interface CalibrationProfile {
  shoulderWidth: number;
  hipWidth: number;
  bodyHeight: number;
  armSpan: number;
  cameraScale: number;
  capturedAt: number;
}
```

### 6.5 舞蹈挑战页 `ChallengeScreen`

目标：当前阶段先闭合流程，不冒充已完成正式游戏判定。

内容：

- 步骤：`04 / 04`。
- 标题：`开始舞蹈`。
- 已载入卡点数：`已载入 N 个卡点`。
- 左侧/主舞台：示范舞蹈视频。
- 右侧/副舞台：`你的摄像头舞台` 占位。
- 占位说明：`下一步会在这里接入实时摄像头、骨架和命中反馈。`

交互：

- 视频保留原生播放控制。
- 返回按钮回到身体校准页。
- 当前不启动用户摄像头，不做评分。

后续挑战页将接入：

- 示范视频与摄像头同步播放。
- 以视频 `currentTime` 作为唯一游戏时钟。
- 按卡点时间窗口结算节奏。
- 对 `手臂打开` 和 `下蹲` 进行动作状态判定。
- 显示 `FULL OUT`、`DROP LOW`、`Perfect`、`Great`、`Early`、`Late`、`Miss`。
- 命中时触发短促荧光粒子和光效反馈。

## 7. 核心交互状态机

当前主流程由 `App` 中的 React 状态管理：

```ts
type PrototypeScreen =
  | "home"
  | "level-select"
  | "analysis"
  | "calibration"
  | "countdown"
  | "challenge";
```

当前实际路径：

```text
home
  └─ 开始游戏 → level-select
level-select
  ├─ 返回 → home
  └─ 选择内置关卡 → analysis
analysis
  ├─ 返回 → level-select
  └─ 确认卡点 → calibration
calibration
  └─ 校准完成 → challenge
challenge
  └─ 返回 → calibration
```

当前会话数据：

- `chart: BeatPoint[]`：用户确认后的卡点列表。
- 内置关卡由 `BUILT_IN_LEVEL` 提供。
- 校准档案当前由 `CalibrationScreen` 生成并通过 `onComplete` 返回；后续可提升为 App 级 session 数据。

## 8. 数据模型

### 8.1 关卡

```ts
interface BuiltInLevel {
  id: string;
  title: string;
  videoUrl: string;
}
```

当前唯一关卡：

```ts
{
  id: "level-1",
  title: "8月3日舞蹈挑战",
  videoUrl: "/levels/level-1.mp4"
}
```

### 8.2 卡点

```ts
type ActionRequirement = "rhythm" | "open" | "squat";

interface BeatPoint {
  id: string;
  beatIndex: number;
  timeSec: number;
  salience: number;
  enabled: boolean;
  action: ActionRequirement;
}
```

字段含义：

- `id`：稳定卡点 ID。
- `beatIndex`：卡点顺序。
- `timeSec`：卡点对应视频时间。
- `salience`：音频能量显著度。
- `enabled`：是否参与挑战。
- `action`：当前动作要求。

### 8.3 姿态帧

```ts
interface PoseLandmark {
  x: number;
  y: number;
  z: number;
  visibility: number;
}

interface PoseFrame {
  captureTimeSec: number;
  landmarks: PoseLandmark[];
}
```

用途：

- 示范视频骨架缓存。
- 用户摄像头实时骨架。
- 手臂角度、髋部高度和身体尺度计算。

### 8.4 判定结果预留

```ts
type TimingGrade = "perfect" | "great" | "early" | "late" | "miss";
type ActionGrade = "hit" | "miss" | "unjudgeable";

interface BeatResult {
  beatId: string;
  timing: BeatJudgement;
  action: ActionJudgement | null;
}
```

当前挑战页尚未正式消费该结果结构，但领域类型已为后续判定和计分预留。

## 9. 卡点与动作判定逻辑

### 9.1 卡节奏

当前已实现的是候选卡点生成和时间轴确认；正式挑战中的节奏评分为后续阶段。

预期评分窗口来自 `GAME_CONFIG`：

```ts
timingWindowsMs: {
  perfect: 100,
  great: 200,
  early: 350,
  late: 350,
}
```

后续挑战以视频媒体时间为唯一游戏时钟。摄像头帧需要记录对应捕获时间，不用模型推理完成时间替代判定时间。

### 9.2 手臂打开

产品定义：

- 任意一只手臂伸直即命中。
- 不要求 X 形。
- 不判断手臂方向。
- 提前伸直并保持到卡点仍有效。

当前示范骨架动作推断使用：

- 肩—肘—腕夹角。
- 伸直阈值约 `155°`。
- 卡点附近窗口约 `±0.25s`。

正式用户挑战时应结合个人校准值和容差，避免不同身体比例带来的误差。

### 9.3 下蹲

产品定义：

- 判断用户身体是否明显降低。
- 不评价专业深蹲技术。
- 不评价膝盖方向、背部姿态或舞蹈风格。

当前示范骨架动作推断使用：

- 左右髋部平均 `y` 值。
- 站立髋部基线。
- 相对下降阈值约 `0.08`。

正式用户挑战时应使用个人校准时的站立高度和下蹲参考。

### 9.4 不可判定

以下情况不应直接判用户失败：

- 肩、肘、腕或髋部不可见。
- 关键点置信度低于阈值。
- 用户部分身体离开画面。
- 摄像头光线或角度导致模型无法识别。

此时给出机位提示，例如“保持全身入镜”，而不是显示动作错误。

## 10. 技术实现路径

### 10.1 技术栈

运行时：

- Vite 5
- React 18
- TypeScript 5
- MediaPipe Tasks Vision
- Browser Web APIs：Canvas 2D、HTMLVideoElement、AudioContext、getUserMedia、requestAnimationFrame

测试与工程：

- Vitest
- Testing Library
- JSDOM
- Playwright
- Vite production build

当前不使用：

- 后端框架
- 数据库
- 登录系统
- 全局状态库
- 路由库
- 大型游戏引擎
- Three.js / WebGL 粒子库

### 10.2 前端流程层

`src/app/App.tsx` 负责：

- 保存当前页面状态。
- 保存当前卡点图谱 `chart`。
- 串联各页面回调。
- 使用 `BUILT_IN_LEVEL` 作为唯一关卡入口。

不在 App 层做：

- 音频分析细节。
- 姿态识别细节。
- 校准计算细节。
- 视觉绘制细节。

### 10.3 页面组件层

`src/components` 负责用户可见界面：

- `HomeScreen`：首页文案、开始操作。
- `ParticleDancerHero`：Canvas 粒子舞者。
- `LevelSelectScreen`：关卡选择和禁用上传入口。
- `AnalysisScreen`：视频、时间轴、卡点操作、示范骨架叠加。
- `CalibrationScreen`：摄像头、骨架、三步采样。
- `ChallengeScreen`：挑战页壳子。

组件原则：

- 接收数据和回调，不隐藏跨页面状态。
- 可测试的用户行为优先于复杂内部状态。
- UI 只做展示和流程编排，领域计算下沉到模块。

### 10.4 音频卡点分析

模块：`src/beat-analysis/energyPeaks.ts`

输入：解码后的单声道 PCM。

当前算法：

1. 按约 `80ms` 窗口切分音频。
2. 计算每个窗口 RMS 能量。
3. 使用能量中位数乘以阈值比例作为候选阈值。
4. 保留局部峰值。
5. 过滤视频首尾边缘。
6. 通过最小间距过滤过密候选。
7. 最多保留约 12 个候选卡点。

默认配置：

- `windowMs = 80`
- `thresholdRatio = 1.35`
- `minSpacingSec = 0.45`
- `edgePaddingSec = 0.25`
- `maxPeaks = 12`

设计取舍：

- 当前不追求严格 BPM。
- 候选卡点是用户可编辑初稿，不是自动完成谱面。
- 算法轻量、可解释、易替换。

### 10.5 示范骨架缓存

模块：`src/analysis/demoPoseCache.ts`

作用：

- 对内置示范视频按固定间隔 seek。
- 调用姿态检测 provider 获取姿态帧。
- 生成 `DemoPoseCache = PoseFrame[]`。
- 提供 `nearestPoseFrame` 根据当前视频时间找最近姿态帧。

当前交互用途：

- 分析页视频叠加骨架。
- 卡点附近高亮手臂或下肢。
- 为 `inferBeatActionsFromPose` 提供参考姿态序列。

设计取舍：

- 只在浏览器会话内缓存。
- 不保存原始视频帧。
- 不要求识别舞蹈动作语义，只作为可视辅助和轻量推断基础。

### 10.6 基于示范骨架的动作推断

模块：`src/analysis/inferBeatActionsFromPose.ts`

当前用途：

- 在分析页根据示范视频骨架自动推断卡点更像 `open`、`squat` 还是 `rhythm`。

逻辑：

- 在卡点 `±0.25s` 窗口查找姿态帧。
- 如果任意一侧肩—肘—腕角度 ≥ `155°`，推断为 `open`。
- 否则根据髋部下降幅度判断是否为 `squat`。
- 否则保持 `rhythm`。

注意：

- 这不是正式“原视频动作识别”能力，只是编辑辅助。
- 用户仍可覆盖卡点动作。

### 10.7 姿态识别

模块：`src/pose`

职责：

- `camera.ts`：启动与停止摄像头。
- `mediaPipePoseProvider.ts`：封装 MediaPipe Pose Landmarker。
- `poseLoop.ts`：以目标 FPS 循环采样视频帧。
- `types.ts`：定义 provider 接口。

配置：

- `poseFps = 20`
- `minimumVisibility = 0.6`

原则：

- MediaPipe 是可替换 provider，不把产品规则写死在模型调用中。
- 姿态帧统一转为 `PoseFrame`。
- 摄像头资源离开页面时必须释放。

### 10.8 身体校准

模块：`src/calibration/calibrationProfile.ts`

当前实现：

- `hasFullBodyInFrame(frame)` 判断肩、腕、髋、踝等关键点是否可见。
- `buildCalibrationProfile(standingFrames, openArmFrames, capturedAt)` 从稳定帧计算最小身体档案。

计算内容：

- 肩宽：左右肩 `x` 距离。
- 髋宽：左右髋 `x` 距离。
- 身体高度：肩部顶部到脚踝底部的 `y` 范围。
- 臂展：左右手腕最大 `x` 距离。
- 镜头尺度：当前以身体高度作为 `cameraScale`。

后续扩展：

- 加入手臂伸直个人阈值。
- 加入下蹲深度。
- 加入中心点、机位签名和 2 秒复核。
- 使用连续稳定帧中位数替代简单平均。

### 10.9 Canvas 粒子与视觉反馈

当前：

- `ParticleDancerHero` 使用 Canvas 2D 绘制首页粒子。
- 粒子数量约 180，reduced-motion 下约 90。
- 粒子由自由漂浮状态周期性向舞者目标点聚合。
- 使用 `requestAnimationFrame` 驱动。
- 使用 OKLCH 色值形成荧光黄绿光感。

后续：

- 将 Canvas 粒子能力复用到挑战命中反馈。
- `FULL OUT` 可使用上扬扩散粒子。
- `DROP LOW` 可使用从地面弹起的低位粒子。
- 性能不足时优先降低粒子数量，而不是影响媒体时钟和姿态采样。

## 11. 视觉规范

### 11.1 视觉基调

FullyDancy 采用沉浸式黑色舞台，不使用普通 SaaS 卡片风。

关键词：

- 冷黑
- 荧光
- 身体轮廓
- 音乐节奏
- 克制的能量感

### 11.2 色彩

- 背景：接近纯黑。
- 主文字：接近白色。
- 主强调色：荧光黄绿色。
- 次要文字：半透明浅灰。
- 错误/警告：克制暖黄，不使用大面积红色。

### 11.3 布局

- 首页：中心标题 + 底部主操作 + 全屏粒子舞台。
- 关卡选择：少量选择项，不做复杂列表。
- 分析页：视频优先，时间轴和操作压缩在底部。
- 校准页：说明 + 摄像头舞台双栏布局。
- 挑战页：示范视频 + 用户舞台双舞台布局。

### 11.4 动效

- 首页有唯一品牌级动效。
- 其他页面动效服务状态变化，不做装饰性 page-load 编舞。
- 卡点选中、骨架高亮和命中反馈可以使用短动效。
- 所有动效必须支持 reduced-motion 降级。

## 12. 隐私与安全

当前隐私承诺：

- 不上传摄像头画面。
- 不上传姿态关键点。
- 不上传校准档案。
- 不上传用户视频，因为当前没有用户上传功能。
- 内置视频作为静态资源公开分发。
- 当前会话数据刷新后可丢失，不做持久化。

上线要求：

- 必须使用 HTTPS，保证摄像头权限可用。
- MediaPipe 模型和 WASM 资源应尽量同源或可信静态托管。
- 页面需明确提示“视频和摄像头数据仅在本地处理”。

## 14. 发布与作品集包装

上线形态：

- 静态 Web 应用。
- 可部署到 Vercel、Cloudflare Pages、Netlify 或其他 HTTPS 静态托管。
- 当前无后端依赖，部署成本低。

作品集表达重点：

- AI 产品边界定义：不做高风险专业舞蹈评分，聚焦可解释动作目标。
- 多模态体验设计：音乐、视频、摄像头姿态、身体校准和实时反馈。
- 本地优先 AI 原型：浏览器端完成音频分析、姿态识别和身体尺度采集。
- MVP 取舍：内置单关卡、无账号、无上传、低复杂度闭环。

建议配套材料：

- 在线体验链接。
- 1 分钟演示视频。
- 产品复盘文章：《从 AI 能力边界出发，设计一个轻量舞蹈练习产品》。

## 15. 后续路线

### 阶段 1：挑战页真实运行

- 接入用户摄像头舞台。
- 同步示范视频和用户姿态帧。
- 以视频时间作为唯一游戏时钟。
- 对卡点进行一次性结算。

### 阶段 2：即时反馈

- 节奏反馈：`Perfect`、`Great`、`Early`、`Late`、`Miss`。
- 动作反馈：`FULL OUT`、`DROP LOW`。
- 命中粒子、闪光和短促视觉反馈。
- 限制负面提示频率。

### 阶段 3：结果页与再来一局

- 总结本轮卡点命中情况。
- 显示节奏准确率和动作完成率。
- 点击再来一局时先做约 2 秒机位复核。
- 机位变化明显时重新完整校准。

### 阶段 4：上线硬化

- 摄像头权限错误恢复。
- 浏览器能力检测。
- MediaPipe 资源加载兜底。
- 移动端布局适配。
- HTTPS 静态部署。

### 阶段 5：未来扩展

- 用户上传视频。
- 多关卡。
- 自定义卡点保存。
- 作品分享。
- 更细分的训练反馈。

这些扩展不进入当前 MVP，只有在核心闭环验证后再评估。
